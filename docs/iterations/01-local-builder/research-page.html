Can a local model build Gravity's issues while Claude plans and reviews?

Yes, it's feasible for small, well-specified, non-UI issues. Whether it saves Claude usage depends on one number nobody has measured: how much of your usage goes to building versus reviewing.

Terms in one minute

Eight words carry most of this report. Skim these once and the rest reads easily.

Open-weight modelA model whose files you can download and run yourself, like Qwen. Claude is not one.
MoE (mixture of experts)A big model that only uses a small slice per word. "35B-A3B" = 35 billion parameters, 3 billion active. Fast on a Mac.
Quantization (4-bit, Q4)Compressing the model's numbers so it fits in memory. 4-bit costs little quality; 2-bit starts to hurt.
Prefill vs decodePrefill = reading the prompt. Decode = writing the answer. On an M1 Max, prefill is the slow part.
Prompt cacheReusing the already-read start of the prompt on the next turn. Turns minutes into seconds when it works.
RuntimeThe program that loads the model and serves it to other programs: llama.cpp, LM Studio, Ollama, MLX.
HarnessThe coding agent that drives the model: reads files, runs commands, opens PRs. Claude Code is one.
B/RClaude usage of one build session (B) divided by one review round (R). The number that decides the pilot.

Failure modes that keep coming up
  • No tool calls, or the call printed as text instead of run.
  • Wrong tool arguments, and retry loops on the same failing call.
  • Reasoning output eating the token budget.
  • Saying "done" when it isn't. One model wrote a helper, never wired it in, and reported success.
  • Gravity-specific risk nobody measured: forgetting a 17 KB rulebook, or deciding a design question instead of flagging it. inference

Five more failure modes Perplexity

  • Procedure compliance without task completion: every checklist heading appears in the PR, but important behaviour is missing.
  • Repository over-reading: context fills fast while real progress stalls.
  • Review amplification: cheap local output creates expensive Claude diagnosis and repeated review.
  • Human subsidy: you quietly clarify, debug or repair the builder, and don't count that work.
  • Policy drift: the local arm quietly gets shorter rules, simpler issues, more hints, or a more forgiving reviewer.

Does it pay? The review bill decides

Taking the build away from Claude saves B. Every extra review round a weaker builder causes costs R. If reviews already cost as much as builds, even a perfect local builder saves only a third.

The arithmetic, in words

A small PR today costs about one build plus two review rounds: B + 2R. B is all the builder-side Claude usage for the issue: the first build plus every fix push between review rounds, and any decision PR the builder drafts. With a local builder all of that moves to the Mac. Planning is a Claude session in both setups, so it cancels out. With a local builder, Claude pays only the reviews, plus Δ extra rounds the weaker builder causes. Share saved = (B − Δ·R) / (B + 2R).

A fuller savings equation Perplexity

Our report uses build vs review. Perplexity adds the other Claude costs a local builder can create:

Saved = B − (Rlocal − Rtoday) − A − F − E
  • B: Claude's build usage today (removed). R: review usage, today vs with local builds.
  • A: extra Claude advice or diagnosis. F: Claude rescue (Claude writing the fix). E: evaluation and maintenance overhead.

Track three outcomes separately, because a local builder can improve one and worsen another: cash (stays within budget), capacity (less Claude usage per accepted issue) and productivity (more accepted work, or less of your attention). The final test: can another project now progress inside the same limits, without slowing Gravity?

Iterations can outweigh model tier: a vendor-curated customer evaluation of 118 app builds averaged 3.6 iterations for Sonnet 5.5 vs 7.7 for Opus 5 (experiment date not disclosed). vendor

Read the detail: how to measure B and R
  • /usage shows plan bars and a 24-hour or 7-day breakdown by skill, subagent and MCP server. On Max, its dollar figures are estimates, not bills.
  • OpenTelemetry export (CLAUDE_CODE_ENABLE_TELEMETRY=1) emits token usage per session, and can tag each session with role, issue and round, e.g. role=review,issue=581,round=1.
  • ccusage reads the local session logs and reports per session. It has no project filter, and builder and reviewer both start in the main checkout, so sessions must be mapped to roles by id, date and first prompt.
  • Two traps. Logs older than 30 days are deleted by default, so export recent Opus builds (#575, #608, #537, #541) now. And npx ccusage on the host is what RULES 10 forbids in a repo session: run it outside any Gravity session with your OK, in a throwaway container with ~/.claude mounted read-only, or rely on telemetry only.
  • Count every Claude cost a local build causes (review rounds, rescue sessions, decision PRs, your Claude-assisted triage), and your own minutes. A drop in Claude usage that raises your minutes per PR is not a win.
  • R includes /code-review high and any subagents it forks (review-pr.md:14-20).
  • The local builder's own sessions also land in ~/.claude/projects, and ccusage may price them at Claude rates, so filter them out by model name.
  • Two non-Claude costs: the laptop is occupied (model, builder stack and any reviewer stack share 64 GB), and your attention is spent (rulings, comments, fixes after an AI APPROVED, as on PR #323).
  • Sources: Claude Code docs, costs · Claude Code docs, monitoring · ccusage session docs · CLAUDE.md:87 (RULES 10) · Arize

  1. Give each measured phase a run ID and role.
  2. Record the exact model and effort setting.
  3. Record the account usage state and reset times.
  4. Avoid unrelated Claude work during the window.
  5. Run the phase.
  6. Capture session data and the new account state.
  7. Reject comparisons that cross a usage reset.
  8. Note any background or concurrent usage that could contaminate it.

Accounting rules: count failed local attempts even when Claude finishes the issue; count extra planning or diagnosis; show results with and without setup overhead; report totals as well as medians (a few expensive rescues can erase many small wins); never compare an easy local issue set with a harder historical Claude set; watch whether review becomes the new bottleneck.

Read the detail: memory formula and context pitfalls (Perplexity)

Memory needed = weights + context cache (KV) + runtime + temporary buffers + concurrent requests, not just the file size. For a standard attention layer:

KV memory = 2 × layers × KV heads × head size × tokens × bytes per value

Example: Qwen3.8-27B has 16 full-attention layers with 4 KV heads of size 256, so ≈2 GiB at 32K tokens and ≈4 GiB at 64K, before anything else. inference Parameter count and context length alone aren't enough to estimate memory.

Context pitfalls to test: early instructions silently dropped; a runtime using a different context limit than you asked for; compaction that loses execution rules or the done-when; big test logs eating the remaining context; reasoning output crowding out the work; an advertised maximum that loads but is too slow to use. A "64K" setting is not 64K of repository: rules, plan, tool schemas, tool results, history and the answer all share it.

Run the full repair loop

The local builder must also fix the review findings. Otherwise you're testing "local first draft plus Claude fixes", not builder replacement. A PR that merges after substantial Claude rescue is a completed issue, but not a local-builder success.

Blind the reviewer, then disclose

Adopted by Yami, 2026-11-12. In both arms, Opus controls included, the reviewer doesn't know who built the PR. The builder session leaves the attribution lines out of the PR body and the commit trailers. The run ledger records the builder from the start. Once the reviewer posts its verdict, a PR comment adds "Built by: <model>", so the record stays complete. Why: LLM judges change their verdicts based on source labels, usually harsher on work labelled as AI-made (arXiv 2510.08831, 2509.26072, 2604.05593). Blinding doesn't remove self-preference, where a model favours unlabelled output that reads like its own (arXiv 2404.13076). That effect would show up as fewer findings per line on the Opus controls, which the ledger can show. No study tests this for code review, so we can't predict which way it goes.

Stop replay leakage

Applies only to the replay stage, where the local model rebuilds past issues Opus already built. "Leakage" means the builder seeing the old answer (the merged code, its PR or its review) and copying it, which would make the score look better than it is. New issues in the forward pilot have no answer to leak.

  • A clean export ending at the base commit, with no later history or solution branches.
  • No merged PR, review discussion or final patch visible.
  • Acceptance checks outside the builder's editable workspace; disposable databases.
  • If an old solution shaped your prompts, that task is a development task, not a held-out test.

Several projects at once Perplexity

Running several projects doesn't need several models generating at once. Start with one local build at a time, as a shared queue: plan and review projects in parallel, but build one at a time. Add concurrency only after measuring throughput and memory, because two builds at once can make both slower. Keep Compose project names, databases, ports, branches and worktrees separate per project.

Leadership lessons

The story worth telling isn't "local models are ready". It's a measured pilot that set its stopping rule before the results, counted review and owner time as costs, and found the binding constraint was the review process, not the model.

19% slowerExperienced developers with AI in METR's 2025 trial, while believing they were faster. Perception ≠ measurement.
+441%Median review time on high-AI teams (Faros, 22,000 developers), with 54% more bugs per PR. Review is the hidden cost.
2.7xSpread in cost per success for one model across four harnesses. The harness is as big a lever as the model.
AmplifierDORA 2025: AI amplifies whatever an organization already is. Gravity's written review policy is the "strong organization" case.
  • Pre-register before you look at results.
  • Measure per merged PR, not per token. Count review load and owner minutes as costs.
  • Verify data locality with a network check instead of assuming it.
  • Be honest about lock-in: open weights reduce model-vendor dependence, but your harness, commands and review process stay Anthropic-shaped.
  • The next lever after the builder is cheaper verification: escalation checkpoints, mechanical pre-review, and a rulebook a smaller model can follow.

  • Perception ≠ measurement. METR 2025: experienced developers 19% slower with AI (95% CI +2% to +39%) while believing they were faster.   • Review is the hidden cost. Faros, 22,000 developers (May 2026): high-AI teams have 54% more bugs per PR and 441.5% longer median review time. Faros DORA 2025: AI raises throughput but also instability. InfoQ on DORA 2025

  • Measure in stages. DX's framework goes utilization → impact → cost, and warns against using these metrics for individual performance. DX

Conclusion from the report. On capability, the answer for small, well-specified, non-UI issues is now plausibly yes. On economics, it's unknown, and Gravity's strict review loop is the reason: a quality gate few organisations have, which charges every weaker build in frontier review rounds. The pilot's most valuable outputs are the B/R ratio and the measured extra rounds Δ. The win from AI builders is capped by what it costs to verify their work.
