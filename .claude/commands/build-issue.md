---
description: Build one GitHub issue end to end and open its PR
argument-hint: <issue number>
---

Build issue #$ARGUMENTS in this repository, the one this session runs in.

1. Read CLAUDE.md and follow it.
2. Read the issue in full from GitHub, including its comments (`gh issue view $ARGUMENTS --comments`, or the GitHub connector). If you cannot read it, stop and ask the owner to paste the issue. If it looks cut off, or contradicts the repo, stop and ask.
   - **BLD-65 read-every-page.** A list this session reads from the GitHub API and then relies on — a review's inline comments, a PR's conversation comments, an issue's comments — is read through every page (`gh api … --paginate`), and the count read is checked against the count the API reports for that list before the round, the issue or the plan is called read in full. The API reports no count for one review's own inline list: there the count is the PR's `.review_comments`, read from the PR's inline list and attributed to the round by `pull_request_review_id`.
   - **An issue this PR carries a closing line for.** (BLD-59).
3. Read every doc the issue cites, at the cited lines (GEN-1).
4. **BLD-48 build-from-the-approved-plan.** At the research and precedent levels this session builds from the issue and the approved plan: it does not re-plan; it decides no design or architecture question itself (BLD-2), while an implementation detail still gets its default (BLD-1); and it raises anything the plan does not cover, or that contradicts it, as a question on the issue (GEN-17). At those two levels, with no approved plan, it stops and says to run `/plan-issue` on that issue.
   - **The three levels, who sets them, and how small an issue is filed.** (GEN-31).
   - **A question this session puts to the owner.** (GEN-17).
   - **Who writes the plan, and what it holds.** (BLD-54, BLD-6).
   - **Amendments to the plan, once it is approved, and the dated line that records the owner's approval.** (BLD-43, BLD-67).
   - **BLD-66 the-body-quotes-every-ruling.** The PR body gives one line to every ruling under the plan comment's "Updated" header, including each one it judges not to reach this build, with why.
   - **BLD-49 level-none-builds-from-the-issue.** At level none there is no plan and nothing waits for approval: the issue is the plan, and this session builds it.
   - **BLD-7 pre-code-doc-check.** Every build, at any level, before coding: check the issue against the docs it cites and the READMEs and runbooks of the folders it changes, and raise every conflict and open question on the issue. The check is the same at all three levels — what differs is the plan around it. They are not left for review to find.
   - **BLD-50 size-rule-after-a-ruling-this-session-gets.** When a ruling this session receives adds a control, a command or a mechanism the issue's "To build" did not list, the size rule (GEN-31) runs again: when the addition is a second independent mechanism, propose building it as its own issue before coding it, and the owner decides.
   - **BLD-52 an-expected-output-block-names-its-surface.** A "You should see" block, or any other expected-output block a PR or a plan writes, names the surface it was captured from — a terminal, a provider's Run log, a local container — and the capture comes from that surface.
5. **SES-11 build-worktree.** Work on a new branch from an up-to-date main, in its own git worktree, `<wt>` below: the builder's path that CLAUDE.md's THIS PROJECT gives, for issue $ARGUMENTS. Make it from the main checkout after `git fetch origin`, with `git worktree add -b <branch> <wt> origin/main`. Build only what the issue says; anything else you find gets its own issue, filed as (GEN-32) says. Run checks and scripts only where CLAUDE.md's THIS PROJECT says.
6. Where the docs are silent, a default goes in the PR body (BLD-1) and a design or architecture choice is flagged and left undone (BLD-2). Any "Question for the owner" in the issue that is still unanswered is left undone too. When the owner answers a question this PR raised, during the build or in review, record the ruling as CLAUDE.md's THIS PROJECT says, and quote the owner's words in this PR's body.
   - **A Low that only corrects the PR's own body.** (REV-2).
7. **BLD-10 screen-before-every-push.** Before opening the PR, and again before pushing each fix round, screen it. An item that fails a screen is fixed or raised; it is never pushed as a default.
   - **BLD-11 defaults-picked.** Check each item against the list of design or architecture decisions (BLD-2), and against every ruling the plan doc records for that area. An item that matches goes under "Questions for the owner", not "Defaults picked", and is left undone.
   - **BLD-12 copied-code-paths.** When the PR copies or replaces a real code path (a function, a script step, a settings block) instead of calling or including it, check the reason in the code and cite it with path:line under "Defaults picked".
   - **Outside tools.** (GEN-20).
   - **BLD-15 rule-text-against-its-ruling.** When the PR writes or amends a rule line, quote in the PR body what authorizes it, beside the line itself, and say that the line is no wider. That is the owner's words, or the rule and commit the line was ported from, when it comes from another repo. One line is compared against one clause; against two at once their union covers anything. For each line the PR writes or amends, the body also names the category its trigger and its object range over, enumerates that category's members from the rule that defines them, and gives each member a covered-or-deliberately-out verdict; the line passes only when every member has one. Where no rule defines the category, the body enumerates it and says that nothing does. A verdict that a reviewer grades the line quotes the (REV-17) entry that makes it true, and a line with no entry says so instead. A line wider than what authorizes it is narrowed, or its width is put to the owner, before the push.
   - **Whether an addition to a rule line is a clause or takes its own id.** (GEN-36).
   - **BLD-16 one-home-per-fact.** When the PR writes or amends a process rule, state the rule once, on the line that carries its id (GEN-24), and cite the id alone everywhere else. A rule that binds builders and reviewers is stated where both read it. Before pushing, list in the PR body every line that mentions each id the PR writes or changes, with `git grep -nE '(<ID>|<ID>)([^0-9]|$)'`, the ids themselves, as in `(BLD-16|GEN-24)`, and say which one defines it. No check script runs here, so the same listing also confirms each cited id is defined once. What no check can see is the same rule restated in prose without its id, which is what this screen and a reviewer are for.
   - **BLD-62 body-list-keyed-on-opening-words.** A list in the PR body that has to stay current across its own pushes keys each entry on the line's opening words, not on a line number. (BLD-40) is where it is re-measured.
   - **BLD-18 rule-copies-outside-the-repo.** When the PR moves or rewrites a rule, check the copies the diff can't show (label descriptions with `gh label list`, issue templates, repo settings and rulesets, and any other copy kept outside the repo) and list them in the PR body.
   - **BLD-39 guard-cost-line.** When the PR adds a guard — a check, a screen, a deny rule, a hook or any other rule — say in the body which failure it prevents and what it costs to maintain. A reviewer may raise a guard that has no cost line.
   - **BLD-40 run-list.** List every runnable thing in the diff and run each one: its tests; every script and every command the diff adds or changes, including one written inside rule text, a doc or a runbook (GEN-16); and every count, list and grep in the PR body or its evidence, re-measured on the head. The PR body carries that list, each entry with its output, or `not run, because …` and the reason (BLD-27).
8. **BLD-19 done-when-and-the-project-checks.** Before opening the PR, run every "Done when" check in the issue, and the project checks CLAUDE.md's THIS PROJECT lists. A "Done when" check this session may not run (THIS PROJECT's host rule), or that needs an account or a provider it cannot reach, is listed in the PR body as the owner's, with the steps they run, and is never reported as run; a check this session may and can run is not listed there.
   - **BLD-57 ci-script-in-a-clean-checkout.** A script the diff adds or changes that CI runs is also run in what CI gives it: a clean export of the head (`git archive HEAD`), which holds no `.env` and nothing untracked, run the way CI invokes it, where THIS PROJECT's host rule says checks run.
   - **BLD-53 walk-from-the-dashboard-home.** A walk of an operator procedure reaches each resource from the dashboard's home, never from where creating that resource left the walker.
   - **BLD-22 checks-assert-an-observable-effect.** Each test or check the PR adds asserts an observable effect (an exit code, a file written, the line a log prints). A timeout is a failure, never a pass.
   - **BLD-23 unreadable-input-is-a-failure.** A check, script or parser the PR adds or changes treats input it cannot read as a failure, with a message saying what to write, never as nothing to check. Its tests include at least one input it does not recognise.
   - **BLD-24 show-the-check-failing.** For each test or check that guards the fix, show it failing on the code without the fix (a throwaway commit or a revert, never pushed), and quote both runs in the evidence. The run asserts that its mutation applied — a replace that matched nothing is a failed run, not a passing check — and the failure it quotes names the guarded behaviour, not an earlier error. Before a throwaway is made the working tree is clean, real work committed or stashed, and the throwaway is made in its own detached worktree, never on the branch.
9. **BLD-25 issue-sweep-before-the-pr.** Before opening the PR, and again after each review round's fixes, search the open issues that touch the changed files or features (`gh issue list --state open --limit 200 --search "<file, folder or feature>"`, one search per changed area; without `--limit` it stops at 30) and apply (BLD-3) to each issue found. Then post one comment on each #M the PR closes, linking the PR's evidence for it (BLD-5). After each fix round, do the same for any new `Closes #M`; if review turns a `Closes #M` into `Refs #M`, comment on #M saying what is left.
   - **An issue this PR closes, read in full before its closing line, through every page of its comments.** (BLD-59, BLD-65).
   - **BLD-27 pr-body-contents.** The body starts with `Closes #$ARGUMENTS`, or with `Refs #$ARGUMENTS` where (BLD-60) or (BLD-61) applies (and any `Closes #M` lines), then "Defaults picked", any open questions in (GEN-17)'s form, what the screens of (BLD-10) ask the body to list, "What I ran" — the run list of (BLD-40), which re-measures those lists — and the evidence with the commit it ran on.
10. **BLD-28 stop-at-ready.** Stop there, once the PR is open and CI has passed on its head, not before, apart from a stop a rule in this command requires — (BLD-48)'s, when no plan the owner has approved exists. A different, fresh session reviews the PR with /review-pr (SES-4).
11. **BLD-29 fix-round-procedure.** When a review round comes back, read the round in full before fixing anything: the review's own body, every inline thread, and the PR's conversation comments since the last push (`gh pr view <N> --comments`, plus the reviews and their threads). The summary is part of the round — its verdict, every finding or partial finding it names, and every question it says is for the owner. Then fix the findings under CLAUDE.md REVIEW POLICY, and repeat the screens (BLD-10), the checks (BLD-19), the issue sweep (BLD-25) and the PR body, whose evidence names the new commit (BLD-27), for the fixes. The reply on the PR lists each item of the summary with what happened to it: fixed, answered, filed, or put to the owner.
    - **BLD-41 questions-before-the-full-runs.** While a question for the owner is open — one the round left, or one the fixes raised — post every question first (GEN-17), then fix only what does not depend on their answers and run only the targeted checks for those fixes: no push that triggers CI, no full run of (BLD-40). When they answer, apply the answers, run everything once (BLD-40) and push, and name in the reply which answers were applied.
    - **BLD-42 measure-a-prescribed-fix.** Before applying a fix a reviewer suggests, check it against the rulings the plan doc records for that area and against the rule ids it touches, and measure the prescription itself against the real data or tree: run its command, grep or count on the head before building it. If a record or the measurement disagrees with it, answer the finding in the PR with the citation or the output instead of applying it.
    - **BLD-51 capture-asked-in-round-one.** A capture only the owner can take is asked for in round 1, before prose derived from a tool's source stands in for the output (BLD-46).
    - **Reading every page of a GitHub list.** (BLD-65).
    - **Evidence a session needs.** (SES-24).
    - **The owner's read of a procedure PR after round 1.** (REV-23).
    - **Repeated findings.** (GEN-22).
12. **SES-13 remove-worktrees-and-branches.** Remove every git worktree and local branch this session created. Once the PR has merged, check `git worktree list`, then run these in order from the main checkout. Each names the build worktree, `<wt>`, because `git branch -d` compares a branch whose upstream is gone with the `HEAD` of the checkout it runs in. First, `git -C <wt> fetch origin` and `git -C <wt> switch --detach origin/main`. Then `git -C <wt> branch -d <branch>` on every local branch this session created. Use `-d`, never `-D`: it refuses a branch with commits that its upstream lacks, or that `origin/main` lacks when the upstream is gone. Last, `git worktree remove <wt>`. Run out of order, a `git -C` on the removed worktree fails with "cannot change to" and deletes nothing. Leave a branch or worktree that git refuses, and quote git's message. Name the worktrees removed and the branches deleted in a post-merge comment on the issue.
